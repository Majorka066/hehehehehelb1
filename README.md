# Планировщик мероприятий

## Тема

Планировщик мероприятий — события и регистрация на них.

## Автор

Мотузок И.С.

## Группа

24ПИ-2

## Описание

Веб-приложение предназначено для планирования мероприятий, просмотра списка событий и регистрации пользователей на мероприятия.

Основной сценарий работы:

1. Пользователь открывает приложение.
2. Просматривает список доступных мероприятий.
3. Выбирает интересующее мероприятие.
4. В дальнейшем сможет зарегистрироваться на выбранное мероприятие.

## Что работает сейчас

В рамках ЛР 7 приложение дополнено связанным названием категории и поиском в Supabase. Реализованы:

- создание нового мероприятия через форму;
- редактирование существующего мероприятия той же формой;
- удаление с подтверждением;
- проверка обязательных полей, даты окончания и рейтинга;
- поиск по названию, фильтрация по статусу и категории и общий сброс;
- отдельные состояния загрузки, ошибки, пустого списка, отсутствующего фильтра и неизвестного адреса;
- общие layout, навигация и адаптивное оформление из ЛР 2.
- категории загружаются из таблицы Supabase `public.event_categories`;
- форма показывает ожидание, ошибку загрузки или пустой справочник и позволяет повторить запрос без потери заполненных полей;
- сохранение доступно только после успешной загрузки и выбора существующей категории;
- после успешной загрузки доступна кнопка «Обновить справочник».
- регистрация и вход по email и паролю;
- защита маршрутов: неавторизованный пользователь перенаправляется на `/auth`;
- загрузка, создание, редактирование и удаление мероприятий через Supabase;
- кнопка выхода из аккаунта;
- RLS-политики: пользователь видит и изменяет только мероприятия со своим `owner_id`.

## Текущие ограничения

В приложении реализована работа только с личными мероприятиями владельца. Таблица `registrations` остаётся закрытой для клиента: сценарий записи на чужое мероприятие в этой лабораторной не добавлялся.

## Настройка Supabase

1. В SQL Editor проекта Supabase выполнить `supabase/migrations/202611030001_initial_schema.sql`.
2. Затем выполнить `supabase/seed.sql`.
3. Для ЛР 6 выполнить `supabase/migrations/202611100001_events_owner_policies.sql`.
4. Для ЛР 7 выполнить `supabase/migrations/202611230001_events_category_filters.sql`.
5. В Dashboard открыть **Authentication → Providers → Email** и включить вход по email.
6. В **Authentication → URL Configuration** задать Site URL `http://localhost:5173` и добавить этот же адрес в Redirect URLs.
7. Скопировать `frontend/.env.example` в `frontend/.env.local` и подставить URL проекта и его publishable key.
8. Перезапустить Vite.

Используются только следующие переменные окружения:

```text
VITE_SUPABASE_URL
VITE_SUPABASE_PUBLISHABLE_KEY
```

`.env.local` не добавляется в Git. Secret key, `service_role` и пароль базы в frontend не используются.

## Схема данных

| Таблица | Назначение | Ключи и доступ |
| --- | --- | --- |
| `event_categories` | Публичный справочник категорий | `id` - PK; доступен только SELECT для `anon` и `authenticated` |
| `events` | Личные мероприятия пользователя | `id` - PK; `owner_id` → `auth.users`; `category_id` → `event_categories`; CRUD только для владельца через RLS |
| `registrations` | Регистрации пользователя на мероприятия | `id` - PK; `owner_id` → `auth.users`; `event_id` → `events`; пока закрыта для клиента |

## Результат ЛР 6

Добавлена авторизация Supabase Auth по email и паролю. Хук `src/hooks/useAuth.ts` получает начальную сессию, подписывается на её изменение и возвращает состояния: проверка, гость или авторизованный пользователь. Страница `src/pages/AuthPage.tsx` позволяет зарегистрироваться, войти и показывает ошибки сервиса.

Маршруты мероприятий вложены в `RequireAuth`: гость перенаправляется на `/auth`, а после успешного входа возвращается на запрошенный адрес. В `AppLayout` показываются email текущего пользователя и кнопка локального выхода.

Сервис `src/services/events.ts` преобразует поля React и PostgreSQL, загружает список и выполняет CRUD в `public.events`. Демонстрационный массив больше не используется: `App` запрашивает записи после появления сессии, а форма ждёт ответ базы и показывает ошибку запроса. Данные сохраняются после обновления страницы.

В миграции `supabase/migrations/202611100001_events_owner_policies.sql` для `events.owner_id` установлен `default auth.uid()`, выданы CRUD-права только роли `authenticated` и добавлены политики RLS. Они разрешают операции только со строками владельца, а при добавлении проверяют совпадение `owner_id` с текущим пользователем.

## Проверка ЛР 6

1. Открыть защищённый адрес без входа: должен открыться `/auth`.
2. Зарегистрировать пользователя A, создать мероприятие и обновить страницу: запись остаётся в списке.
3. Выйти из A, зарегистрировать пользователя B: запись A не должна быть видна.
4. Войти снова как A, отредактировать, отменить изменение и удалить своё мероприятие.
5. В Network показать запросы к Supabase, затем выполнить `npm run build` и `npm run preview`.

## Контрольные вопросы и ответы (защита ЛР 6)

1. **Что хранит сессия Supabase?** Она связывает браузер с авторизованным пользователем и содержит токены, по которым Supabase определяет `auth.uid()`.
2. **Почему после `signUp` иногда нужно подтвердить email?** При включённом подтверждении Supabase создаёт пользователя, но не выдаёт активную сессию до перехода по ссылке из письма.
3. **Зачем состояние `checking`?** Пока приложение не получило сессию, нельзя считать пользователя гостем и преждевременно отправлять его на страницу входа.
4. **Чем `RequireAuth` отличается от RLS?** `RequireAuth` скрывает страницы в интерфейсе, а RLS защищает строки непосредственно в базе. Для безопасности нужны оба уровня.
5. **Чем `USING` отличается от `WITH CHECK`?** `USING` выбирает существующие строки для чтения, изменения и удаления. `WITH CHECK` проверяет новую строку при добавлении или её новое состояние после изменения.
6. **Почему для UPDATE нужна ещё политика SELECT?** После обновления Supabase может возвращать строку клиенту; доступ к ней также должен быть разрешён политикой SELECT.
7. **Что произойдёт, если пользователь B укажет id записи A?** RLS не даст её прочитать, изменить или удалить, потому что `owner_id` не равен `auth.uid()` пользователя B.
8. **Почему publishable key можно хранить в frontend?** Он не обходит RLS. Безопасность обеспечивают токен пользователя, права и политики базы; secret key в браузер добавлять нельзя.

## Результат ЛР 7

Основная сущность — `events`, связанный публичный справочник — `event_categories`. Сервис выбирает событие вместе с `event_categories(id, name)` одним запросом. В карточке показывается имя категории, а форма сохраняет её стабильный `id`. Внешний ключ из первой миграции уже использует `ON DELETE RESTRICT`: используемую категорию удалять нельзя. Новая миграция добавляет индексы для отбора по владельцу и статусу, а также по `category_id`. Таблица `registrations` остаётся закрытой и в этом сценарии не используется.

Фильтры: текст названия, статус и категория. Черновик панели не отправляет запрос при каждом вводе. «Применить» передаёт условия в `getEvents`, где `ilike` и `eq` добавляются к запросу Supabase. «Сбросить» очищает поля и повторно загружает список. Символы `%` и `_` в текстовом поле являются шаблонными символами `ilike`; длина поиска ограничена 100 символами.

Пустой список предлагает создать первое событие, пустой ответ с фильтрами сообщает «Совпадений нет», ошибка сети показывает кнопку повтора. Сохранение возвращает строку со связанной категорией, а карточка запрашивается по `id`, поэтому работает при прямом открытии. При ошибке форма сохраняет черновик и разблокирует повторную отправку.

Проверка: создать события разных статусов и категорий; применить текст, статус и их сочетание, затем сброс; открыть карточку по прямой ссылке и обновить страницу; изменить категорию; отключить сеть во время сохранения и повторить; проверить удаление события и доступ другого аккаунта. Запустить `npm run build` и `npm run preview`. В чистой копии выполнить `npm ci`, миграции по порядку, настроить `.env.local` по образцу и повторить сценарий.
